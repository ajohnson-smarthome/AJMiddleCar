# Design

## Context

Мотивация — в `proposal.md`. Что есть на входе: код трёх компонентов, `docs/protocol.md` и `contract/*.json` как правда о проводе, `README.md`, `CLAUDE.md`, `docs/bringup.md` как правда о стенде, 62 замороженных design-документа в `docs/superpowers/specs/` и хост-тесты (`firmware/*/test`, `app/tests/*`, `tools/mock_car/test_*.py`, `tools/conformance*.py`), которые уже закрепляют часть поведения.

Пишут 25 агентов в параллельных worktree, каждый — одну capability, не видя чужих. Единственное, что их выравнивает, — этот документ и пилот `specs/car/rt-link/spec.md`.

## Goals / Non-Goals

**Goals:**
- 26 спек одной глубины и одной формы, пригодных как база для дельт.
- Каждая спека проверяема: сценарий — потенциальный тест, а не пересказ.
- Ноль дублирования с `docs/protocol.md` и контрактом.

**Non-Goals:**
- Не переносить `docs/superpowers/` в OpenSpec — это история решений, не поведение.
- Не исправлять код, документы и контракт, даже если спека выявила расхождение.
- Не описывать внутреннее устройство: приоритеты задач, имена файлов и структур, выбор библиотек.

## Decisions

**Раскладка — `specs/<область>/<capability>/spec.md`, четыре области.** `car`, `dongle`, `app`, `shared`. Плоский список из 26 имён смешал бы три процессора и приложение; koteychik использует тот же двухуровневый приём (`tma/…`, `backend/…`). Область — это компонент, у которого свой код и свой билд; `shared` — то, что держит их вместе.

**Глубина — наблюдаемое поведение, и только оно.** В спеку попадает то, что видно снаружи модуля: провод, REST, домены `/config` и их диапазоны, слова состояния в `/status`, тайминги, режимы отказа, и **инварианты безопасности, на которые опираются другие модули** («никогда оба HIGH», «единственный писатель PCA9685», «арбитр по рангу»). Не попадает: приоритет задачи, имя функции, что парсер без malloc, как устроен ring buffer. Проверка: если реализацию можно заменить, не меняя того, что видит пульт, стенд или другой модуль, — это не спека.

**Числа — по ключу контракта, не по значению.** `rt.watchdog_ms`, а не «300 мс»; `video.chunk_bytes`, а не «1200». Значение живёт в одном месте и меняется одним коммитом; спека, повторившая его, устареет молча. То же для байтов провода: «заголовок по `docs/protocol.md` → Wire format», а не таблица полей. Спека говорит, *что машинка обязана сделать* с тем, что описано там.

**Код — правда, документы — второй источник, стенд — третий.** Порядок при расхождении: код → хост-тест → `docs/protocol.md`/контракт → `README.md`/`CLAUDE.md` → `docs/bringup.md` → `docs/superpowers/`. Спека пишется по коду. Расхождение с любым документом — отдельный issue (`orca linear create --parent-current`), в спеке — как в коде, в PR — одна строка «расходится с X, заведён AJM-N». Чинить нельзя: change без изменений кода остаётся без изменений кода.

**Пилот первым, остальные — на него.** `car/rt-link` написана при propose, PM-сессией вместе с пользователем, и утверждается вместе с этим планом. Задача 1.1 — не «написать», а «прочитать и сверить с кодом»: пилот тоже проходит через воркера, чтобы форма была проверена тем же путём, каким пойдут остальные. Все прочие задачи заблокированы ею в Linear.

**При propose создаётся одна спека, не 26.** Схема ждёт файл на каждую capability до начала работ; здесь написание спек и есть работа. `openspec validate` требует хотя бы одну дельту — она есть. Это осознанное отступление, а не пропуск.

**Бюджет спеки — 6–12 требований, 1–3 сценария на требование.** Пилот — 11 требований. Меньше шести — capability, скорее всего, часть соседней; больше двенадцати — две capability под одним именем. В обоих случаях воркер пишет об этом в PR и не режет молча: границы меняет PM-сессия через `/opsx:update`.

**Язык.** Текст по-русски; `SHALL`/`MUST`/`SHALL NOT` по-английски; структурные заголовки (`Purpose`, `ADDED Requirements`, `Requirement:`, `Scenario:`, `WHEN`/`THEN`) — по-английски, как требует `openspec/config.yaml`. Имена требований и сценариев — по-русски, валидатор это принимает (пилот проходит `--strict`).

**Что смотреть — в задаче, не в спеке.** Каждый пункт `tasks.md` перечисляет файлы, разделы документов и тесты, из которых capability читается. В спеку имена файлов не попадают (спека — контракт, не библиография); в описании PR — да, чтобы ревью могло проверить каждое требование по источнику.

**Проверка в PR воркера.** `openspec validate ajm-2-baseline-specs --strict` — форма; `CONFORMANCE=required tools/test-all.sh` — дерево цело (спека кода не трогает, но правило процесса одно для всех PR). Ревью PM-сессии — по источникам из описания PR: каждое требование должно находиться в коде.

**Archive.** Когда все 26 пунктов в Done — `/opsx:archive` переносит дельты в `openspec/specs/**`; `Purpose` каждой копируется из дельты. После archive `CLAUDE.md` получает одну строку: `openspec/specs/` — базовая линия поведения, дельты пишутся от неё.

## Risks / Trade-offs

- [25 авторов — 25 глубин] → пилот как образец, бюджет 6–12, ревью каждого PR по источникам; спека вне бюджета возвращается на доработку, а не принимается «пока так».
- [Пересказ `protocol.md` вместо ссылки] → правило «числа по ключу, байты по разделу»; ревью отклоняет спеку, в которой есть литерал, у которого есть ключ в контракте.
- [Спека по документу, а не по коду] → порядок источников выше; сценарий, которого воркер не нашёл в коде или тесте, помечается в PR как «по документу, в коде не найдено» и решается PM-сессией.
- [Стендовое поведение без стенда] → `car/radio-and-network`, `dongle/panel`, `dongle/usb-network` описывают то, что записано в `docs/bringup.md` и `firmware/dongle/README.md` как наблюдённое; предположения из «Open assumptions» в спеку не попадают.
- [Конфликты в `tasks.md`] → каждый PR меняет одну свою строку; соседние строки сливаются тривиально; воркер делает rebase на `origin/main` перед PR.
- [26 PR на ревью одному человеку] → это цена «всё»; порядок групп в `tasks.md` — от самых ценных для ближайших change'ей (`car`) к наименее (`shared`), чтобы остановка на полпути оставила полезный остаток.
